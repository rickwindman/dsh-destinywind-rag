## 二、选型结论

**选定 `Soren-ABT/dsh-knowledge` v0.5.2 作为二次开发基础。**

### 为什么选它

1. **需求几乎逐条命中**：描述即「chunking, local embeddings, hybrid search, management panel」，与「文档解析/分块/索引/检索 + embedding provider 抽象 + 管理面板」完全对齐。
2. **技术栈与约束一致**：Node 原生 `node:sqlite`（`DatabaseSync`）+ SQLite **FTS5** 虚拟表、`@huggingface/transformers` 4.3.1 + `onnxruntime-node` 本地 ONNX、BM25 + 向量 + RRF 混合检索 —— 正是用户要求的「嵌入式方案：SQLite + 本地 BM25 + transformers.js/ONNX」。
3. **provider 抽象层已成型**：`embedTexts(provider, baseUrl, model, apiKey, texts, signal)` 单入口，`provider ∈ openai | ollama | local | none`，扩展成本低。
4. **配置三层合并已实现**：插件 Config 默认值 → 全局运行时覆盖 → 每知识库覆盖，且每库可独立绑定 embedding/rerank/分块参数 —— 直接支撑「每个知识库绑定不同 provider」。
5. **UI slot 机制现成**：`inject = ['slots','locale']` + `slots.inject('settings.section' | 'sidebar.footer.action' | 'shell.overlay', ...)`，注册设置页栏目是既有能力。
6. **工程完备**：CI、vitest 单测（40+ spec）、benchmark、smoke、打包校验、双语 README 齐全。

### 主要风险 / 代价

| 项 | 说明 |
|---|---|
| **许可证 AGPL-3.0** | 传染性许可证。二次开发后分发须同样以 AGPL-3.0 开源并标注来源。**需用户确认接受**。 |
| 体量较大 | 226 文件、`knowledge/index.ts` 218KB、UI `KnowledgeSection.tsx` 132KB，理解成本高。 |
| 默认零配置为「关」 | 默认 `embeddingProvider: 'none'`（退化为纯关键词），与需求「零配置开箱可用」有差距，需新增自动检测。 |
| 绑定模型为「每库覆盖字段」 | 现为每库直接写 provider 字段（一对一），需求要的是 **provider 注册表 + 多对多引用**，需重构。 |
| 入口位置不同 | 现为「侧边栏底部入口 + 全屏浮层面板」，需求要的是 **设置页【知识库】栏**，需改注册点。 |

## 三、研究点逐条回答

### 1. 文档解析、分块、索引、检索主流程怎么组织

```
导入 → parse.ts（解析）→ chunk.ts（分块）→ embed.ts（向量化）→ chunkdb.ts（落库+FTS5）
                                                                        ↓
提问 → tool-knowledge/knowledge_search → knowledge/index.ts（编排）
     → retrieval.ts（BM25 + 向量 + RRF 融合 + MMR）→ rerank.ts（可选重排）
     → context.ts（上下文组装/去重/截断）→ 返回带来源的 chunk
```

- **解析** `src/knowledge/parse.ts`（26.8KB）：`mammoth`(DOCX)、`mupdf`/`pdfjs-dist`/`pdf-parse`(PDF)、`turndown`(HTML→MD)、`word-extractor`、`@firecrawl/anydoc`；另有三档文档处理器 `builtin | mineru | mineru-local`（MinerU 负责复杂 PDF 结构化 + OCR）。
- **分块** `src/knowledge/chunk.ts`（16.6KB）：`smartChunk` 智能切分、`structuredChunking` 结构化分块、`semanticChunk` 语义分块（嵌入段落级片段后按余弦阈值合并）、`chunkTokenLimit` token 预算切分、`chunkSeparator`/`chunkSize`/`chunkOverlap`。
- **索引** `src/knowledge/chunkdb.ts`（61.2KB）：`node:sqlite` 的 `DatabaseSync`；`CREATE TABLE chunk` + `CREATE VIRTUAL TABLE chunk_fts USING fts5(...)`；含 `document_generation_stage/chunk/commit` 三张表做**事务化代际索引**（中断可恢复，避免半成品索引污染检索）。
- **检索** `src/knowledge/retrieval.ts`（9KB，240 行，纯函数、无 IO，易测）：见下。

检索核心（`retrieval.ts`）：

| 能力 | 实现 |
|---|---|
| 分词 | `tokenize()`：拉丁词小写化（长度>1）+ **CJK 字符 bigram**（单字回退），中文友好、确定性 |
| 词法 | `buildBm25()`，`k1=1.5`、`b=0.75`；`normalizeBm25(raw)=raw/(raw+1)` 归一到 [0,1) |
| 向量 | `cosineSimilarity()`，向量预归一化，点积即余弦 |
| 融合 | `reciprocalRankFusion()`，**RRF_K = 60**，支持每路权重 `weights[]`（对应配置 `rrfVectorWeight`） |
| 多样性 | `maximalMarginalRelevance()`，MMR 去冗余 |
| 编排 | `rank(query, candidates, options)`：auto 模式下按「有向量则 hybrid，否则 lexical」自动降级；再阈值过滤 + topK 截断 |

### 2. embedding provider 抽象层怎么设计的

单入口分发（`src/knowledge/embed.ts` 第 84–110 行）：

```ts
export async function embedTexts(
  provider: EmbeddingProvider, baseUrl: string, model: string,
  apiKey: string, texts: readonly string[], signal?: AbortSignal,
): Promise<number[][]>
```

- `'none'` → 抛错并提示「配置端点或本地模型，或保持词法检索」（降级为纯 BM25）
- `'local'` → `embedLocal(model, texts)`，走**独立 child process**（`embed-worker.ts` + `embed-protocol.ts` 版本化 IPC）运行 transformers.js；默认模型 `onnx-community/Qwen3-Embedding-0.6B-ONNX`（约 585MB / 1024 维）
- `'openai'` → `embedOpenAI(baseUrl, model, apiKey, texts)`，OpenAI 兼容 `/embeddings`
- `'ollama'` → `embedOllama(...)`，空 baseUrl 回退 `http://127.0.0.1:11434`

配套的本地模型治理（值得直接沿用）：
- `poolingFor(modelId)`：Qwen3→last_token、BGE/BCE→cls、E5/GTE→mean，未知回退 mean
- `isLocalModelDownloaded()`：真实校验 `config.json` + `onnx/*.onnx` + tokenizer 三件套非空
- `LocalModelStatus { model, status: idle|downloading|ready|error, progress, message }` + `getLocalModelStatus()` 供设置页轮询
- **staging 目录 + 真实向量 probe 通过后才提升为正式缓存**，并写 `.dsh-embedding-ready.json` 指纹 marker
- `localWorkerIdleTimeoutMs`（默认 60s）空闲卸载 ONNX session 但不杀进程

### 3. 配置 schema 与默认值在哪定义

- **插件 Config（schemastery）**：`src/knowledge/config.ts` 第 105–151 行 `export const Config: Schema<Config>`，约 45 个字段，含 `embeddingProvider: Schema.union(['openai','ollama','local','none']).default('none')`、`chunkSize: 1024`、`chunkOverlap: 200`、`topK: 6`、`searchMode: 'auto'`、`rrfVectorWeight: 1` 等。
- **部署默认值**：`cordis.patch.yml` 的 `knowledge` 行 `config:` 块。
- **三层合并**：`resolveConfig(config, overrides)`（部署默认 → 全局运行时覆盖）与 `resolveConfigFor(config, overrides, baseConfig)`（再叠加每库覆盖），全部字段带 `clampInt/clampNumber` 边界钳制。
- **运行时覆盖持久化**：`src/knowledge/domain.ts` 的 `configOverridesSchema`（zod），存于 domain global slot。
- **API Key 来源优先级**：`overrides.embeddingApiKey ?? process.env.KNOWLEDGE_API_KEY ?? config.embeddingApiKey`（rerank 同理走 `KNOWLEDGE_RERANK_API_KEY`）—— 已支持环境变量读取。

### 4. 索引存储用什么方案

- **文档与知识库元数据**：DSH 存储域 `defineDomain({ name:'knowledge', version:0, global:{...}, tables:{ bases, documents } })`（`domain.ts`），zod 校验，`@deepseek-ai/dsh-storage-domain` 落地。
- **分块与全文索引**：**SQLite 单文件** `node:sqlite`，默认 `<DSH_HOME>/storages/knowledge-chunks.sqlite`（`chunkStorePath` 可覆盖），`chunk` 表 + `chunk_fts` **FTS5 虚拟表**。
- **向量存储**：分块向量以 `number[]` 形式随 chunk 记录存放（未用 sqlite-vec 扩展，属纯 JS 余弦计算）。→ 这是与用户「优先 sqlite-vec」的一处差异，可在改造点中评估是否引入。
- **模型权重缓存**：默认 `<DSH_HOME>/cache/dsh-knowledge/local-models`（`localModelCacheDir` 可覆盖）。

## 五、待用户确认的关键分歧

1. **许可证**：基础项目为 **AGPL-3.0**，改造后分发须同样 AGPL-3.0 开源。是否接受？若不可接受，需改为仅参考设计、独立实现（工作量显著增加）。
2. **多对多含义**：需求写「知识库与 embedding 模型多对多」，但同库内混用不同维度向量会导致检索不可比。倾向实现为「多库复用同一 provider + 每库独立绑定一个 provider」，是否认可？
3. **本地模型默认**：内置 ONNX 默认模型 `Qwen3-Embedding-0.6B-ONNX` 约 585MB，首次使用需联网下载。是否接受此默认？
4. **入口形态**：需求要「设置页【知识库】栏」，基础项目现为「侧边栏底部入口 + 全屏浮层」。是否改为设置页栏目（或两者并存）？
