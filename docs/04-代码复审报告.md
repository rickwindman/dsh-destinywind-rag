## 二、缺陷清单与修复

### 🔴 高严重度

#### D1. 换绑模型后继续导入 → 产生混合维度索引（数据损坏）

- **复现**：库用 4 维模型建索引 → 换绑 8 维模型（标记 stale 但不强制重建）→ 继续导入新文档 → 库内同时存在 4 维与 8 维向量，`indexDim=8` 掩盖事实。跨维度余弦相似度无意义，等于静默产出坏索引。
- **修复**：`#ingest` 加维度一致性守卫——库里已有向量（`indexDim>0`）且本次成功拿到向量时，维度不一致直接拒绝导入，中文提示「请先重建索引」。
- **回归**：`复审R5`。

#### D2. 重建期间状态被覆盖

- **复现**：`reindexBase` 开头设 `indexing`，但 `#rewriteEmbeddings` 每完成一个文档就把状态写回 `ready`——多文档重建时 UI 上「索引中」只闪一下。
- **修复**：状态只在开头（`indexing`）与结尾（`ready`/`partial`）各写一次，中途不回写。
- **回归**：`复审R8`（断言中途不得出现 `ready`）。

#### D3. HTTP API 无同源校验（跨源写攻击面）

- **复现**：处理器不校验 `Origin`。恶意页面可用 `fetch(..., {mode:'no-cors'})` 发 POST——虽读不到响应，但重命名/删除知识库、改配置这类「只写不读」操作恰好够用。
- **修复**：`sameOrigin()` —— 无 `Origin`（curl/模型工具等非浏览器客户端）放行；有 `Origin` 时必须与 `Host` 一致，否则 403。
- **位置**：`index.js` `makeHandler` 入口。

### 🟡 中严重度

#### D4. 换绑到「维度未知」的 provider 不触发需重建

- **复现**：provider 从未测试过（`dim=0`），换绑后库状态仍是 `ready`。旧向量由旧模型生成，新模型维度未知，唯一安全姿态是要求重建。
- **修复**：`bindProvider` 记录换绑前的旧 provider，三种情况触发 `stale`：维度已知且不一致 / 换到维度未知的 provider / 同 provider 换了模型名。
- **回归**：`复审R1`、`复审R2`（重复绑定同一 provider 不误报）。

#### D5. 修改 provider 模型名后，绑定的库全部不失效

- **复现**：`updateProvider` 改 `model` 后，两个绑定它的库都仍显示 `ready`。模型名 = 向量源，改了就必须重建。
- **修复**：`updateProvider` 检测 `model` 变更，把 `listBasesBoundTo(id)` 的库全部标 `stale`；只改显示名不触发。
- **回归**：`复审R3`、`复审R4`。

#### D6. 重排序 fetch 无超时

- **复现**：`#rerank` 的 `fetch` 无 `AbortController`。重排端点挂起会拖死整个检索请求（而 `embed.js` 的远程调用都有 30s 超时，唯独这里漏了）。
- **修复**：8 秒硬超时，超时抛中文错误并建议「关闭重排序继续用混合检索」。
- **回归**：源码级确认（`AbortController`/`signal`/`clearTimeout` 就位）+ 既有用例「重排序失败不阻断检索」仍通过。

#### D7. 插件无 dispose → 热重载泄漏 DB 句柄

- **复现**：`apply` 未注册卸载回调。DSH 停用/热重载插件时，SQLite 连接不关闭——Windows 下文件被占用，后续删除 profile 会失败。
- **修复**：`ctx.effect(() => () => svc.close(), ...)` 注册释放回调（关 DB + 卸载模型内存）。

#### D8. 每库配置覆盖完全没接线

- **复现**：`search`/`#ingest`/`reindexBase` 三处都写死 `resolveConfigForBase(config, null)`——需求明确要求「每个知识库可独立绑定不同参数」，实际每库覆盖形同虚设。
- **修复**：新增 `base_overrides` 表 + `get/setBaseOverrides`；三处链路改走 `#configForBase(baseId)`。
- **回归**：`复审R9`（库1 `topK=1` 真实生效，库2 按全局）、`复审R10`（空值恢复继承）。

### 🟢 低严重度

#### D9. 重建性能 O(N×M)

- **复现**：`reindexBase` 对每个文档都调一次 `loadCandidates`（全库扫描）。5 个文档 → 5 次全库加载；1000 文档 → 1000 次全表 JOIN。
- **修复**：一次加载、按 `documentId` 分组（O(N×M) → O(M)）。
- **回归**：`复审R7`（断言恰好加载 1 次）。

#### D10. 向量化失败的降级导入把 `indexDim` 清零

- **复现**：库已有 4 维索引 → 某次导入时向量化失败（`dim=0`）→ `addDocument` 无条件 `setBaseIndexDim(baseId, 0)` → 维度校验从此误判「尚未建立索引」，需重建判定失效。
- **修复**：仅 `newDim > 0` 时更新 `indexDim`。
- **回归**：`复审R6`。

#### D11. `addDocument`/`deleteBase`/`deleteDocument` 多条写操作无事务

- **风险**：中途失败留下「有文档无分块 / FTS 与 chunk 不一致」的半写状态。
- **修复**：新增 `transaction(fn)`（显式 BEGIN/COMMIT/ROLLBACK），三处全部包进单事务。
- **回归**：`复审R11`（构造分块主键冲突 → 断言文档记录被整体回滚）。

#### D12. OnnxRuntime 并发 `#load` 竞态

- **风险**：并发首次调用同一模型 → 多个 in-flight 加载同时跑 → 重复下载 + 泄漏 pipeline 实例。
- **修复**：`inflight` Map 去重，同模型并发共享同一加载 Promise。
- **回归**：源码级确认（`inflight` 就位）。

#### D13. 杂项

- `#ingest` 中未使用的 `lines` 变量（死代码）→ 删除。
- `/fs/list` 可对任意绝对路径 `readdir`（系统目录探测）→ 加 `isBrowseAllowed` 约束（仅 Documents/Downloads/Desktop 及子目录）。

## 五、复审仍未覆盖的已知边界（如实说明）

1. **并发导入同一库**：维度守卫挡住了「跨模型混维」，但两个并发导入同一库仍可能交错写（SQLite WAL 下写仍是串行的，数据不会损坏，但文档顺序不保证）。
2. **`base_overrides` 尚无设置页 UI**：表与读取链路已就位（每库覆盖真实生效），但 UI 暂未提供编辑入口，需通过 HTTP API 设置。
3. **ONNX 真实链路未测**：本机未安装 `@huggingface/transformers`，本地 ONNX 分支仅有「运行时不可用→中文降级提示」的测试，真实推理路径需装依赖后验证。
4. **`lineNumberAt` 的 O(n²)**：字符偏移→行号仍是逐字符扫描，60 万字符 × 84 分块在本机 <1ms（未超阈值），但复杂度未优化；超大文档可预构建行号索引。

## 六、真实启动排障记录（v1.0.0 首次实机启动失败的两轮定位）

### 第一轮：`EADDRINUSE 127.0.0.1:3080`（非本插件）

启动日志显示 DSH 自身 webserver 绑定 3080 失败（残留旧进程占用），连锁拖垮 12 个插件。
09-29 的日志证明**装本插件之前该问题就反复出现**。当前机器已恢复正常。

### 第二轮：`web boot: dsh-destinywind-rag: import failed`（本插件，真凶）

崩溃日志（`crash-2026-10-10T17-15-40-171Z-web-boot.log`）给出决定性证据：

```
renderer console: Uncaught SyntaxError: Identifier 'API_BASE' has already been declared
    at dsh-app://app/plugins/??dsh-destinywind-memory/client.js,...,dsh-destinywind-rag/client.js,...
```

- **根因**：DSH 的 web boot 把**所有插件的 client.js 拼接进同一个模块作用域**（URL 可见：`??a/client.js,b/client.js,...`）。本插件在 client.js **顶层**声明了 `const API_BASE`，与 `dsh-destinywind-memory/client.js` 顶层的同名声明相撞 → 整个拼接模块 SyntaxError → import failed → DSH 无法启动。
- **为什么此前的验证全部漏过**：单文件语法正确（`node --check` 通过）、stub 加载正确（IIFE 隔离）、124 个测试全绿——**只有真实拼接时才炸**。这是一类「多插件共享作用域」的集成缺陷，任何单插件视角的测试都覆盖不到。
- **修复**：`const API_BASE` 移入 `factory(require)` 函数作用域（其他本机插件均如此），并全机扫描确认顶层声明唯一性（memory 的 `API_BASE` 是全机唯一顶层声明，rag 移入后无撞名源）。
- **防御**：client.js 头部新增「拼接安全」注释，明确顶层禁止声明任何标识符。

### 伴随发现：`plugin add` 对 bundles 不幂等

对已安装的插件再次执行 `dsh plugin add` 会重装依赖，但 **`dsh.profile.bundles` 里的行可能被丢掉**（两次安装实测一次保留一次丢失），形成「依赖在、装载行不在」的半挂载状态。
**操作规程**：每次 `plugin add` 后必须核对三处对齐——`dependencies` / `dsh.profile.bundles` / `node_modules`；缺 bundles 行时手工补回。

### 伴随发现：`github:` 依赖声明会让重装走 ssh 通道而失败

`dsh plugin add https://...` 首次安装时 pnpm 走 https tarball 通道，成功；
但装完后 profile 的 dependencies 里留下 `github:owner/repo` 声明，**再次 add/install 时
pnpm 会按该声明走 `git+ssh://git@github.com` 解析 ref**，本机无 SSH key 必然
`Permission denied (publickey)` 失败。

**修法**：把声明改成锁定 commit 的形式 `github:owner/repo#<sha>`（本机其他 destinywind
插件即此形态），pnpm 便按 https 拉取。`allowBuilds` 白名单同样必需（pnpm-workspace.yaml），
否则 onnxruntime-node 的安装脚本被拒。注意 onnxruntime-node 1.30.0 的 Windows 二进制在
`bin/napi-v6/win32/x64`（Node 24 的 ABI 是 v6，不是旧文档里的 v3）。
