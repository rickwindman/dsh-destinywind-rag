## 一、选型过程

### 1.1 候选可用性核查

调研方式：`gh api` 直连 GitHub（`web_search` 因余额不足不可用）。用户给出的 5 个候选中，**只有 2 个真实存在**：

| 候选 | 结果 | 结论 |
|---|---|---|
| **dsh-knowledge**（优先） | ✅ [Soren-ABT/dsh-knowledge](https://github.com/Soren-ABT/dsh-knowledge) v0.5.2，226 文件 | **选定** |
| dsh-rag (imkelt) | ❌ 未检索到该 owner 下的同名仓库 | 不可用 |
| dsh-plugin-rag (mervyn-teo) | ❌ 未检索到 | 不可用 |
| dsh-docintel | ✅ [LL-cmyk-so/dsh-docintel](https://github.com/LL-cmyk-so/dsh-docintel) | 备选，但**无向量检索**（仅 SQLite FTS5 关键词） |
| bailian-kb-dsh | ❌ `total_count: 0` | 不存在 |
| *dsh-kb-rag（额外发现）* | ✅ [Breeze136/dsh-kb-rag](https://github.com/Breeze136/dsh-kb-rag) | 不选：**依赖 Python 引擎**（`kb_engine.py` + MCP server），部署重 |

### 1.2 为什么选 dsh-knowledge

1. **需求逐条命中**：官方描述即「chunking, local embeddings, hybrid search, management panel」。
2. **技术栈与约束一致**：`node:sqlite` + FTS5、`@huggingface/transformers` + `onnxruntime-node`、BM25 + 向量 + RRF —— 正是要求的「SQLite + 本地 BM25 + transformers.js/ONNX」嵌入式方案。
3. **provider 抽象层已成型**：`embedTexts(provider, baseUrl, model, apiKey, texts, signal)` 单入口，`provider ∈ openai|ollama|local|none`，扩展成本低。
4. **三层配置合并已实现**：插件 Config → 运行时覆盖 → 每库覆盖，支撑「每库独立绑定模型」。
5. **工程完备**：CI、40+ vitest spec、benchmark、smoke、打包校验、双语 README。

### 1.3 关键决策：不直接 fork，而是「沿用架构 + 按本机规范重写」

**这是本次最重要的技术判断。**

上游项目是 **TypeScript + 构建链**，其 `package.json` 的 devDependencies 依赖：

```
"@deepseek-ai/cordis": "link:../dsh/vendor/cordis"
"@deepseek-ai/dsh-host-webserver": "link:../dsh/packages/host/webserver"
"@deepseek-ai/dsh-storage-domain": "link:../dsh/packages/storage/storage-domain"
...
```

这些 `link:../dsh/...` 指向 **DSH 源码 checkout**。经实测本机 `D:\Programs\DeepSeek Harness\resources\app.asar\dsh` **不存在**（只有安装包，无源码），因此上游**无法在本机构建**。

同时，本机已装的 8 个 `dsh-destinywind-*` 插件揭示了本机可行的插件形态：

| 项 | 本机规范 |
|---|---|
| 语言 | 纯 JavaScript（ESM），`"type": "module"` |
| 构建 | **零构建**，源码直接运行 |
| 宿主半 | `index.js`（导出 `inject` + `apply`） |
| 浏览器半 | `client.js`（`window.__ModuleLoader__.load` + React） |
| 挂载 | `cordis.patch.yml`（`- insert: - id / name`） |
| 本地化 | `locale/zh.json`、`locale/en.json` |

**结论**：沿用 dsh-knowledge 的**算法与架构设计**（BM25 参数、CJK bigram、RRF、MMR、provider 单入口、池化映射、三层配置），按**本机插件规范以纯 JS 重新实现**。这既满足了功能需求，又保证插件在本机真正可运行、可安装。

### 1.4 Slot 名称：读真实 Slot 树，不猜测

需求要求「管理界面注册到设置页」与「输入框旁的选择器」。这两个 Slot 名**通过 DSH 自带的 Inspect 工具读取真实 Slot 拓扑获得**，而非猜测：

```json
// cordis_inspect_query(platform: "client", provider: "Slots", method: "listSubTree")
"settings.section"          // kind: list — One settings page per list entry.
"conversation.input.left"   // kind: list, scope: session — Compact controls at the left of the composer tool row.
```

最终注册：

| Slot | 用途 | id | order |
|---|---|---|---|
| `settings.section` | 设置页【知识库】栏 | `destinywind-rag` | 18 |
| `conversation.input.left` | 输入框旁知识库范围选择器 | `destinywind-rag-scope` | 30 |

### 关于 #12（斜杠命令）

需求标注为「可选补充」。当前已实现两条调用路径（输入框选择器限定范围 + 模型自行调用工具），斜杠命令属于便捷入口，未实现不影响核心验收。**如需，可后续补充。**

### 关于 #14（sqlite-vec）

**评估结论：本版本不引入。** 理由：

- 向量以 `Float32` 的 JSON 数组存在 `chunk.embedding` 列，检索时在 JS 内做余弦计算。
- `sqlite-vec` 是 SQLite 扩展，`node:sqlite` 内置模块**不支持加载扩展**（需 `loadExtension`，而 `node:sqlite` 未暴露该能力）。
- 引入需改用 `better-sqlite3`（原生模块，需编译），与「零构建、零原生依赖」的目标冲突。
- 在数千至数万分块规模下，JS 内余弦 + FTS 预筛的性能可接受（实测 112 个用例的检索均在数十毫秒内）。
- **触发引入的条件**：单库分块数 > 5 万且检索延迟成为瓶颈时，再评估换用带扩展能力的 SQLite 驱动。
